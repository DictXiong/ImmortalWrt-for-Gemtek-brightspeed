# Airoha 桥接兜底绑定与生命周期

## 故障条件

`9990-net-airoha-bind-WLAN-bound-flows-on-PPE-driver-L2-cache-miss.patch`
在驱动 L2 缓存缺少父流时，使用网桥 FDB 解析出口并直接绑定 PPE 子流。
RX 学习发生在普通网桥的 `should_deliver()` 检查之前。

当目的 MAC 已被学习到当前入口，旧实现仍可能绑定入口等于出口的路径。
即使该有线桥端口的 hairpin 关闭，后续报文也可能被硬件送回原端口。
多台有线 AP 接在同一网桥时，这种反射可以形成返回通路。桥接绑定保持
TTL/Hop Limit，使三层跳数不能终止这类二层循环。

另一处缺口是兜底绑定缺少父流的生命周期管理。FDB 删除或移动后，直接
绑定的槽位可能继续使用旧出口。现场已分别观察到同口反射和 FDB 删除后
IPv6 旧绑定保留，具体内核分支仍应结合目标构建及实验结果判断。

核对实际物理入口、所属网桥、双端口 forwarding 状态和同端口 hairpin 许可。
入口支持普通桥端口、VLAN 和 br_netfilter 物理入口上下文。无法确认路径时
保留软件转发。新增只读 RCU STP 查询接口，供 NAPI 接收上下文调用，既有
RTNL 查询接口保持原有调用约定。

提供通用网桥硬件活动查询接口，具体老化语义见下节。

`9999-22-net-airoha-track-bridge-flow-lifecycle-and-activity.patch` 为桥接槽位记录
namespace、网桥、入口、出口、入口 VID 及源/目的 MAC，同时实现硬件活动查询。

- 同桥同 VID 的源 MAC 在原入口收到 FDB ADD，或目的 MAC 在原出口收到 FDB ADD，保留已有记录和有效绑定。不同端口的 ADD 表示移动，DEL 表示删除，均撤销相关兜底绑定。

- 解析路径前读取变更计数器，提交时在 PPE 锁内复核，避免把事件发生前的旧路径提交到硬件。

- 撤销复用既有单播提交流程，统一处理 NPU 统计及 SRAM 写回。硬件读取或撤销失败时保留跟踪标记并输出限速诊断，供后续相关事件再次处理。

## 硬件活动与 FDB 老化

PPE 命中的报文绕过软件网桥，软件 FDB 的 `updated` 时间可能停止更新。
`offload` 标志本身不能阻止 Linux 对动态 FDB 老化。直接监听所有删除并撤销
PPE，会让活跃硬件流随着软件 FDB 老化而退出卸载。

`9999-21-net-bridge-query-offloaded-source-activity-before-FDB-aging.patch`
新增 `SWITCHDEV_FDB_GET_LAST_USED` 查询事件，让网桥仅在动态条目即将老化时
通过 switchdev 查询硬件源地址活动，既有事件编号保持原值。
Airoha 根据仍受跟踪的 BND 槽位及硬件时间戳返回最近活动时间，核对
namespace、网桥、VID、入口端口和源 MAC。查询沿用 RCU 与 PPE 锁，
没有新增后台定时任务。未报告活动的驱动沿用原有老化行为。

桥接 IPv4 也可能由已有 TC 三层流接管。完整 Airoha 补丁同时为这些已核对桥接
路径的普通 TC 流保留源地址活动上下文。活动记录与撤销所有权
分开，普通 TC 流继续由既有父流管理硬件生命周期，直接兜底流才由本补丁撤销
硬件槽位。普通驱动覆盖槽位时先移除旧记录，再按当前路径登记活动。

活动查询只更新已有条目的时间，不创建条目或改变出口。显式删除、MAC 移动、
端口事件仍撤销绑定。并发更新通过比较交换及删除前复核处理，`ageing_time=0`
保留原有清表语义。

只有报文源地址证明设备仍在该入口。持续向静默目的端发送数据不会延长其
FDB 寿命。因此，双向活跃流应保持卸载，只有单向发送且目的端长期静默的流
仍可能正常老化并回到软件转发。

## 验证方法

必须先证明 NPU 已附加，并找到探针对应的硬件学习条目。启动后的第一次
有效卸载请求前，PPE 可能尚未初始化，不能把这时的零反射算作修复成功。

采用隔离的额外以太网测试口及自动清理，网关另有精确的返回流量保护。
按 IPv4/IPv6、native VLAN 1/VLAN 192 分组，分别检查以下行为。

1. 已知目的 MAC 位于入口端口且 hairpin OFF 时，不建立 BND，也不从该端口返回探针。
2. 正常跨端口流量能完整交付并建立对应 BND。
3. 删除实验源/目的 FDB、移动目的 MAC 或实际执行端口 DOWN 后，旧绑定撤销。
4. 端口恢复及重新学习后，正常流重新交付并绑定。
5. 显式允许的隔离端口 hairpin 能交付和绑定，结束后先移除实验 FDB，再恢复策略。
6. 真实无线客户端验证双栈业务、接收端吞吐、访客 VLAN 与隔离，另行验证 MLO。
7. 持续双向流跨越默认 FDB 老化周期，核对硬件时间戳、FDB 时间、删除通知及绑定状态。
8. 对照静默目的端、显式删除和链路变化，确认活动查询不会把失效路径永久保留。
9. 动态 FDB 改为同端口静态项，确保实际触发 ADD，核对源／目的通知后原槽位保持 BND，且相同 MAC 的另一 VLAN 不受影响。再验证跨口 ADD 和同口 DEL 仍能撤销。

关闭 USB 主机侧 MAC 不一定让 AP 的 PHY 失去载波。断链验收需读取 AP 实际
端口状态，不能仅凭操作命令成功作结论。
